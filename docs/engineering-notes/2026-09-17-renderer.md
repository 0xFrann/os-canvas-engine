# 2026-09-17 — Renderer: the API moved under us, and the first frame is empty

Two things worth writing down from building `@os-canvas/renderer`.

**The attribute names changed.** Chrome's feature page still describes the canvas opt-in as
`layoutsubtree`, but the current WICG explainer and Chromium's IDL use `content="drawable"` on
the canvas plus a bare `drawable` attribute on each child (Chromium keeps `layoutsubtree` behind a
`TODO: remove`). Went with the new names, but kept them as exported constants
(`CANVAS_CONTENT_ATTRIBUTE`, `DRAWABLE_ATTRIBUTE`) rather than string literals, since this is
still a dev-trial API and the safe assumption is that it moves again.

**You can't draw an element the same task you inserted it.** `drawElementImage` needs a recorded
snapshot, and snapshots are recorded during the browser's rendering update — so a mount created
inside `render()` throws `InvalidStateError: No cached paint record for element` if drawn
immediately. The API's own answer is the `paint` event: the canvas fires it once the new
drawable has a snapshot. So `render` catches that one error, calls `canvas.requestPaint()`, and
moves on. Deliberately did *not* catch everything — a mount that isn't actually a canvas
descendant should still blow up loudly.

Smaller one: paint order used to be a private helper in `hit-testing`. The renderer needs the
exact same ordering or "topmost drawn" and "topmost picked" diverge, so it moved to `document`
as `paintOrder(doc)` and both import it. It felt slightly wrong to put something paint-flavored
in the document package, but it's a pure function of `anchor` and `zIndex`, which are document
fields — the alternative (renderer importing from hit-testing) was more wrong.

Not yet verified in a real Canary — tests run against fakes. That's the first job for Step 6.
