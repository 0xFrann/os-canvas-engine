# 2026-09-17 — Renderer: the API moved under us, and the first frame is empty

Two things worth writing down from building `@os-canvas/renderer`.

**The attribute names are mid-rename, and the explainer is ahead of shipped Chrome.** The WICG
explainer and Chromium *main* use `content="drawable"` on the canvas plus a bare `drawable`
attribute on each child. I built to that, opened the PR, and only then ran it in a browser
(Chrome for Testing 153 with `--enable-blink-features=CanvasDrawElement`): blank desktop.
`drawElementImage` threw `InvalidStateError: DrawElementImage requires the canvas to have the
layoutsubtree attribute` — the shipped build only knows the old boolean `layoutsubtree`, and
`canvas.content` isn't even a property there. Chromium main reads `content` first and falls back
to `layoutsubtree` (kept behind a `TODO: remove`), so the renderer now sets both. Names stay as
exported constants since this will move again.

**The lesson isn't about attribute names.** It's that I shipped a renderer nobody could see. Unit
tests with fakes proved the math; they cannot prove the browser does anything, and for a project
whose entire point is an experimental browser API that's the only proof that matters. The
renderer is now wired into `apps/shell` in the same PR and `pnpm screenshot` drives a
flag-enabled Chrome over CDP to look at it. That's the bar from here on: not done until it's on
screen.

**You can't draw an element the same task you inserted it.** `drawElementImage` needs a recorded
snapshot, and snapshots are recorded during the browser's rendering update — so a mount created
inside `render()` throws `InvalidStateError: No cached paint record for element` if drawn
immediately. The API's own answer is the `paint` event: the canvas fires it once the new
drawable has a snapshot. So `render` catches that one error, calls `canvas.requestPaint()`, and
moves on. First version matched on the error *name* only — which is how the `layoutsubtree`
failure above became a silent 60Hz `requestPaint` loop instead of a stack trace. Now it matches
the message too, and everything else rethrows.

Smaller one: paint order used to be a private helper in `hit-testing`. The renderer needs the
exact same ordering or "topmost drawn" and "topmost picked" diverge, so it moved to `document`
as `paintOrder(doc)` and both import it. It felt slightly wrong to put something paint-flavored
in the document package, but it's a pure function of `anchor` and `zIndex`, which are document
fields — the alternative (renderer importing from hit-testing) was more wrong.

**Pixels were right, hit-testing was not.** Once it rendered, selecting text by dragging in one
window highlighted the *other* window's text, and double-clicking a paragraph selected content
from the window next to it. Measured it: every mount's `getBoundingClientRect()` was `(0, 0)` at
its natural size, at DPR 1 and 2 alike. In Chrome 153 `drawElementImage` returns the DOMMatrix it
recorded but does nothing with it for hit-testing, there's no `updateElementGeometry`, and
`getElementTransform(el, matrix)` (two args in this build) doesn't move anything either. So the
top-left of the canvas was a pile of three invisible hit boxes and the last-drawn one won.

The fix that worked: position each mount with CSS — `transform: translate(x, y) scale(zoom)`,
`transform-origin: 0 0`, `position: relative; z-index: <paint index>`. The explainer says the
snapshot is taken *before* CSS transforms, and it is: the drawn output is pixel-identical, while
`elementFromPoint` now returns the right window at zoom 1 and 1.5 and a real mouse click on a
close button closes that window. It's a workaround for the shipped build, not the design, and
it's flagged as such in `docs/renderer.md`.

**And the content was invented.** The first wiring seeded a "Clock" and an "About" window because
they were handy. Neither exists in the reference desktop this project is a port of — its apps are
Example, Example Two and Settings. That's a made-up feature that everything after it would have
quietly built on. Replaced with the reference apps and window chrome (`AppsWindow`, header +
close, Roboto Mono, its CSS variables), and `ContentKind` now mirrors the reference's `APPS_DATA`.

Verified on Chrome for Testing 153 (`--enable-blink-features=CanvasDrawElement`): two windows in
z-order, hit-testing correct at zoom 1 and 1.5, taskbar pinned through the `ResizeObserver`.
